# Release

This is the maintainer's runbook: how a release is made by the pipeline (#73),
the checklist it has to pass, and how an unsigned build is checked.

## How a release is made

Nobody builds on a laptop. Four workflows do it:

1. **`release-plz.yml`, job `release-plz-pr`** runs on every push to `main`. It
   reads the conventional commits since the last tag and opens or updates the
   **release PR** (label `release`): the version bump and `CHANGELOG.md`
   (rendered by git-cliff from `cliff.toml`; `release-plz.toml` is the
   configuration). A PR that the built-in token opens starts no workflow, so
   the job starts `ci.yml` on the PR branch itself (`workflow_dispatch`); the
   `ci-ok` result sits on the PR's head commit.
2. **You merge the release PR** once `ci-ok` is green and the checklist below
   is done.
3. **`release-plz.yml`, job `release-plz-release`** sees the merge and creates
   the tag `v<version>` (release-plz does not create a GitHub Release: release.yml
   does, so exactly one tool creates it). A tag pushed with the built-in token
   starts no workflow either, so the job starts `release.yml` on the tag with
   `workflow_dispatch`.
4. **`release.yml`** builds `x86_64-pc-windows-msvc` natively on
   `windows-2025` and `aarch64-pc-windows-msvc` on `windows-11-vs2026-arm`
   with `cargo auditable` (the dependency list is embedded for `cargo audit
   bin`), checks the exe against the size budget, writes the third-party
   licences, packages and attests the zip and the bare exe, then builds the
   CycloneDX SBOM and `SHA256SUMS` (attested too) and creates the GitHub
   Release from the section of `CHANGELOG.md` (a pre-release for a tag with a
   `-` in it, such as `v0.1.0-rc.1`). Afterwards **`release-verify.yml`**
   downloads the published assets on both runners and checks the checksum,
   the attestation (`gh attestation verify`), a smoke run (`--diagnostics`
   exits 0), a Defender scan of the zip and `cargo audit bin` of the exe.

No token or secret is involved: everything uses the built-in `GITHUB_TOKEN`.
The one thing it cannot do is fire a `push` or `pull_request` workflow, which
is why the two jobs above start `ci.yml` and `release.yml` by
`workflow_dispatch` (a trigger the built-in token may fire).

Assets of a release `v<version>` (immutable once published):

| Asset | What |
| --- | --- |
| `peekbuddy-v<version>-<target>.zip` | the exe, `LICENSE`, `README.md`, `THIRD_PARTY_LICENSES.html`, for `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc` |
| `peekbuddy-v<version>-<target>.exe` | the same exe on its own |
| `peekbuddy-v<version>.cdx.json` | the CycloneDX SBOM |
| `SHA256SUMS` | the checksum of every other asset |
| GitHub attestations | one per asset (`gh attestation verify`) |

No PDB is released: the exe is built stripped, and a symbolised trace is made
from a profiling build of the same commit (`cargo build --profile profiling`,
see [Profile](profile.md)).

`release.yml` is written by hand, not generated by dist: dist cannot host the
signing step of #74 between the build and the archive, and its generated
workflow does not pass zizmor. A pull request that changes `release.yml` or
`release-verify.yml` runs the build jobs (no publishing), which is the
rehearsal of the pipeline.

The signing step of #74 goes between the build and the archive; today the
step `Unsigned build` of `release.yml` only logs it.

If a job of `release.yml` fails, fix the cause and run the workflow again on
the same tag (`gh workflow run release.yml --ref v<version>`); `gh release
create` refuses to replace a release that exists. A release that was
published with a wrong asset is not repaired by uploading over it (see the
last section): delete the release and the tag, bump the patch version.

## Release checklist

Open the issue from the *Release checklist* template
(`.github/ISSUE_TEMPLATE/release_checklist.md`) for every release candidate and
release. Each item needs an evidence link: a workflow run, a dashboard, a PR or
a screenshot. Nothing is ticked without one.

The checklist covers, in order:

1. **Product**: the MUST features of the roadmap are done, spikes and ADRs
   agree with what shipped, the exe runs unelevated and opens no network
   connection during a 10-minute end-to-end session.
2. **Performance**: every row in `perf/budgets.toml` is calibrated; the
   deterministic rows are green on both runners; the timing rows are within
   budget on the nightly trend for 7 days on both architectures. A single PR
   wall-clock run is never evidence (ADR 0007).
3. **Correctness**: the zero-undetected-loss suite, durability and migration
   tests, and the UI suite with the UIA smoke on the release build are green.
4. **Quality gates**: mutation results reviewed, coverage targets met, CodeQL
   and Scorecard clean, `cargo audit` and cargo-deny clean, Miri and fuzzing
   green nightly.
5. **Release artifacts**: `SHA256SUMS`, attestations, SBOM and third-party
   licences present; the release notes carry the *unsigned build*
   note; `release-verify` is green.
6. **Docs**: the tutorial, how-tos, reference and explanation pages are
   current; the README has current screenshots and the *Unsigned builds*
   section.
7. **Launch**: the site listing is ready, the announcement is drafted, and
   after the release is public any Defender
   false positive is reported.

## Checking an unsigned build

Follow [Verify a download](verify-download.md) on the release assets, and try a
tampered copy: both the checksum and the attestation must fail on it. Never
re-upload an asset under the same version: SmartScreen's reputation is per file
hash, and a replaced asset breaks every checksum already published. A fix is a
new patch version.
