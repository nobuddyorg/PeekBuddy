# Performance

PeekBuddy has to be fast and invisible: a tray app that runs all day and
never shows up in a battery report. This page defines every performance
budget, how each one is measured and where it is gated.

The numbers live in [`perf/budgets.toml`](perf/budgets.toml), the single
source of truth read by `cargo xtask perf` (#27), `cargo xtask bench-ab`
(#26), the allocation tests (#23) and the size gate (#28). The table below is
generated from it; `cargo xtask budgets --check` fails CI when they disagree.
The decision behind the policy is [ADR 0007](docs/adr/0007-performance-gate-policy.md).

## Metric classes

- **Deterministic**: the same code gives the same number on every machine
  (allocation counts, undetected-loss count, binary size, handle counts,
  timer counts). Gated strictly on every PR.
- **Timing**: wall-clock or CPU time. Noisy on shared runners, so never gated
  against an absolute number on PRs.
- **Resource**: memory and similar. Trended nightly.

## Gate policy

F11, verbatim: deterministic metrics gate strictly; wall-clock metrics gate
only through same-runner interleaved A/B comparison (at least 10 alternating
samples, medians, **warn at +15 %, fail at +50 %**); the nightly trend
**alerts at +25 % against the rolling median**; thresholds are recalibrated
after **2 weeks** of nightly data.

F10, verbatim: **zero allocations per event on the capture path after
warm-up**; bounded allocations per writer batch and per viewer frame. The
capture path is parse, filter and classify up to the hand-off to the ring;
the writer and the viewer have their own budgets (`alloc.writer_per_1000`,
`alloc.viewer_per_frame`).

Gate values in `budgets.toml`:

| gate | meaning |
| --- | --- |
| `pr-strict` | every PR; any violation fails `ci-ok` |
| `pr-ab` | every PR; same-runner A/B, warn +15 %, fail +50 % |
| `nightly-ab` | nightly A/B against the previous main |
| `nightly-trend` | nightly; alert at +25 % against the rolling median |
| `report-only` | measured and reported, never gated (owner-PC runs, targets) |

Each row in `budgets.toml` has: `id`, `metric` (definition), `unit`,
`bound` (`max` or `min`), `limit` (absent while an issue still sets it),

## Instrumentation

ETW TraceLogging provider (`crates/peekbuddy-win/src/perf/etw.rs`, #21):

| | |
| --- | --- |
| Name | `NoBuddy-PeekBuddy` (tools also accept `*NoBuddy-PeekBuddy`) |
| GUID | `{69eb5350-8420-5c03-5c05-1a6dafc0df73}` (name hash; a unit test pins it) |
| Keyword `0x1` | `Milestone` events: `Name`, `Role` (`engine`/`viewer`), `SinceProcessCreateUs` |
| Keyword `0x2` | `Counters` events: events received, rows persisted, overflows, gaps, ring-depth high-water mark, last batch size; written on batch commit, never from a timer (F6) |

Milestones (each recorded in the in-process table read by `--perf-probe`
(#24) with the same timestamp as the ETW event):

| Milestone | Recorded when |
| --- | --- |
| `ProcessStart` | `main` entered |
| `SettingsLoaded` | settings read and validated |
| `StoreOpened` | store opened and writable |
| `WatcherArmed` | one root armed (once per root) |
| `TrayShown` | tray icon added |
| `EngineReady` | tray added **and** all watchers armed (F7) |
| `ViewerSpawn` | engine started the viewer |
| `ViewerFirstFrame` | first presented frame with the first page of rows (F7), measured from the viewer's own process creation |
| `Overflow`, `Gap` | buffer overflow, gap row written |
| `ReconcileStart`, `ReconcileEnd` | reconciliation scan |
| `SegmentRotate` | new day segment opened |

`SinceProcessCreateUs` is computed in-process from `GetProcessTimes`
creation time. ETW is diagnostics only: it can drop events under pressure.

Process metrics (`peekbuddy_win::metrics`, #24) take any process handle
opened with `PROCESS_QUERY_LIMITED_INFORMATION`, so the harness samples the
engine from outside without waking it:

| Field | API | Note |
| --- | --- | --- |
| `private_bytes` | `K32GetProcessMemoryInfo` (`PROCESS_MEMORY_COUNTERS_EX.PrivateUsage`) | commit charge; never mixed with the working set |
| `working_set`, `peak_working_set` | same | include shared pages |
| `page_faults` | same | soft and hard |
| `creation`, `kernel`, `user` | `GetProcessTimes` | 100 ns ticks |
| cycles | `QueryProcessCycleTime` | same machine and frequency state only |
| handles | `GetProcessHandleCount` | `engine.handles.stable` |
| GDI / USER objects | `GetGuiResources` | |
| I/O bytes and operations | `GetProcessIoCounters` | `engine.startup.disk_read` |
| context switches | `NtQuerySystemInformation(SystemProcessInformation)`, summed over the process's threads | buffer reused, 0 allocations per sample (`alloc_perf`); `None` when unavailable |
| architecture | `IsWow64Process2` + build target | emulated processes give meaningless numbers |

Context switches stand in for wakes (`engine.idle.wakes`): every wake is at
least one switch-in, so the count is an upper bound on wakes. PDH is banned
(`cargo xtask check-deps`).

Recording a trace: `wpr -start perf\peekbuddy.wprp!PeekBuddy.Light -filemode`,
run PeekBuddy, `wpr -stop out.etl`, open in WPA.
`wpr -start perf\peekbuddy.wprp!PeekBuddyStartup -filemode` adds disk I/O,
file I/O and hard faults. (WPR reads `Name.DetailLevel`, so the startup
profile cannot be called `PeekBuddy.Startup`.) CI records the `etw_smoke` example on every
PR (job `etw smoke (windows x64)`) and uploads the ETL.

## Profiling with Tracy

Developer-only build (#22); no Tracy code ever ships.

```sh
cargo xtask profile --tracy [--alloc] [--role engine|viewer]
```

| | |
| --- | --- |
| Profile | `[profile.profiling]`: `inherits = "release"`, `debug = "line-tables-only"` (set `"full"` for variables), `strip = "none"`, PDB next to the exe |
| Feature `profile-tracy` | `tracing` spans become Tracy zones; the role's whole run is one zone (`engine` or `viewer`) |
| Feature `profile-tracy-alloc` | adds `ProfiledAllocator` (call-stack depth 8) around the counting allocator (#23) |
| Versions | `tracing-tracy` 0.12.0, `tracy-client` 0.19.0, `tracy-client-sys` 0.30.1, Tracy GUI **0.14.1**; pinned exactly, bumped together by hand |
| Client features | `enable`, `ondemand`, `only-localhost`, `sampling`, `context-switch-tracing`; the defaults `broadcast`, `code-transfer` and `crash-handler` stay off |

`ondemand`: nothing is buffered until a viewer connects (without it the
client keeps every event in RAM). `only-localhost`: no LAN broadcast, no
remote listener. Call-stack sampling and context-switch capture need an
elevated process; zones and plots do not. Overhead, not gated: about 2.25 ns
per zone; a call stack costs about 98 ns at depth 1 and 1.37 us at depth 60.

Guards:

- `cargo xtask check-release` fails when the release feature set pulls in
  `tracy-client-sys` (`cargo xtask check` and `test (windows x64)`), and with
  `--exe` when the release exe contains `___tracy` or `Tracy` (`test
  (windows x64)` scans `target/release/peekbuddy.exe`).
- `profiling.yml` builds the profiling exe on `windows-2025` and
  `windows-11-vs2026-arm` weekly and on PRs that touch it, runs both roles
  and checks that both guards reject that build.

The `profiling` crate (issue text: 1.0.18 with `profile-with-tracy`) is not
used: 1.0.18 depends on `tracy-client` 0.18.5 / `tracy-client-sys` 0.29.0
(the Tracy 0.14.0 protocol), which would link a second, incompatible client.
Library code annotates with `tracing` spans instead.

## Runner assumptions

The repository is public (#4): hosted Windows runners have 4 vCPU and 16 GB.
Every timing baseline assumes `windows-2025` (x64) or
`windows-11-vs2026-arm` (arm64, Defender on). Bare-metal numbers come from
scripted owner-PC runs (#84).

## Recalibration

A row moves from `provisional` to `calibrated` only through a PR that cites
evidence (a spike report `docs/spikes/NNNN-*.md` or at least 2 weeks of
nightly data), updates `status` and adds a changelog line below. Loosening any
budget also needs an ADR amendment in `docs/adr/`.

- #33: `viewer.first_frame.*`, `viewer.private_bytes.10m_rows` (and its arm64
  row).
- #34: which rows can run on hosted runners at all.
- #35: `store.bytes_per_event`, `event.latency.*`,
  `query.filter_first_results`, `export.1m_rows`.
